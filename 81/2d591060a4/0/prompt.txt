## 1. Blocking Issues

None. I specifically tried to break the suppression heuristic and could not construct a permanent data-loss scenario:

- **`markExecCallsCovered` marks *all* pending calls covered** (`src/agents/codex/codex-agent.ts:387-390`): CommandExecution events carry no `call_id` (verified in the sample — the item has `id: "exec-…"`, no call reference), so per-call association is impossible and mark-all is the only option. The risky window (a foreign CommandExecution arriving while call B is pending) requires overlapping scripts, and even then B's real content still surfaces unconditionally via its own later CommandExecution line — only the model-assembled duplicate is dropped, which is the documented intent.
- **Eviction is fail-safe** (`codex-agent.ts:381-383`): evicting the oldest pending call only risks *showing* a duplicate, never hiding data; `markExecCallsCovered` uses `set` on existing keys so Map insertion order (and thus "oldest") is preserved.
- **Fallback correctness**: CLI &lt;0.148 (no CommandExecution → never marked) and late-yielding commands (output arrives while `covered === false`) both display the output, confirmed by tests at `tests/codex/code-mode.test.ts:296-303` and `:318-326`, and by the sample's strictly sequential call/output ordering.

## 2. Suggestions

- [`src/agents/codex/codex-agent.ts:547`] `const callId = payload.call_id as string;` — unsafe cast; the sibling call site (line 525) correctly guards with `typeof callId === 'string'`. A missing `call_id` happens to work (`Map.get(undefined)` → `undefined` → output shown), but the cast hides that; mirror the guard for consistency.
- [`src/agents/codex/codex-agent.ts:623-626`] `truncate(..., { headLength: 80, tailLength: 40 })` on the script injects `\n\n… (N chars omitted) …\n\n` (chalk-colored) into the `$ ` header, making a single command render as a 3-line block. Consider `truncateByLines` with `headLines: 1` or a single-line ellipsis so one command stays one visual line.
- [`src/agents/codex/codex-agent.ts:387-390`] Add one sentence to the `execOnlyCalls` doc comment stating that CommandExecution has no `call_id`, so coverage is intentionally attributed to *all* pending calls, and that any wrongly-marked call's content still appears via its own CommandExecution line. This is the subtlest invariant in the diff and is currently only implicit.
- [`src/agents/codex/codex-agent.ts:469-472`] `getDisplayType` returns `'output'` for every `item_completed`, including UserMessage/AgentMessage/Reasoning, which `format` then reduces to `''` (line dropped). Harmless but slightly misleading; the existing comment covers it — fine to leave.
- [`tests/codex/code-mode.test.ts`] Coverage gaps worth adding: (a) an exec-only `write_stdin` script (the other `EXEC_TOOL_NAMES` member — currently untested end-to-end), (b) the `MAX_TRACKED_EXEC_CALLS` eviction path, (c) `commandExecutionScript` with an empty array or non-string elements (currently renders as a bare `$ `).
- [`src/agents/codex/codex-agent.ts:524-531`] Pre-existing, but now on the hot path: `parseCodeModeCalls` runs twice per `custom_tool_call` line (once in `format`, once in `getToolName`). Not introduced by this diff; noting only since exec scripts can be large.

## 3. Questions

- Should the suppressed `custom_tool_call_output` show a placeholder in verbose mode (e.g. `[output suppressed — shown via CommandExecution]`)? — If a script prints `text()` extras beyond command output (e.g. `"summary: " + r.output` prefixes), those fragments are silently dropped when covered; a verbose-only hint would make the suppression auditable without affecting normal rendering.
- Is `exec_command`/`write_stdin` the complete exec-tool surface for CLI ≥0.148? — If Codex later adds e.g. `exec_patch` or renames these, scripts using them would fall outside `EXEC_TOOL_NAMES` and silently revert to showing the model-assembled output (safe but duplicated). A periodic re-check against a fresh sample would keep this honest.
